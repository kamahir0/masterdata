# Product Direction

Status: Direction

この文書は製品の目的と設計判断の軸を示す。個別の操作、保存単位、型、ファイル形式等のApproved仕様は[Specifications](../specs/README.md)で定める。

## 目指すもの

MasterDataの構造を理解しながら、表計算ソフトやテキストエディタのように、データと定義を少しずつ作り、直せるデスクトップ編集環境。

ユーザーが欲しい結果は、書き直し自体や共通基盤の完成ではなく、日常の編集を軽快かつ予測可能に進められる製品である。

## 設計の出発点

- GUI単独の製品として、実際の作業シナリオから要求を導く。CLIの操作API、実行単位、完成済みデータを前提にした手順を編集モデルの制約にしない。
- 編集途中の未完成・不整合を保持して修正できる方向を目指す。診断、編集、保存、build / publishの役割を整理し、具体的な許容範囲は操作・失敗シナリオから仕様化する。
- 初心者の発見可能性と、繰り返し使う人の効率を両立する。機能数やクリック数だけを最適化しない。
- 部品や型の組み合わせが変わっても、同じ概念を同じ方法で操作できるようにする。選択・フォーカス・編集・保存の状態を区別して伝える。
- 操作前の予想と実際の挙動を一致させる。誤操作を回復でき、入力を予期せず失わず、修正方法が自然に見つかることを重視する。
- データを主役にし、必要な場所で操作できる配置、標準的なキーボード操作、読みやすい情報階層、落ち着いたfeedbackを整える。
- 必要な機能と作らないものを選ぶ。外部のGitツール等で足りる作業を、無条件にアプリへ取り込まない。

## 仕様を評価する代表作業

以下は仕様を導くためのシナリオ候補で、機能一覧や完成範囲の自動承認ではない。

| 作業 | 確認する体験 |
| --- | --- |
| 表と項目を作り、値を入力する | 完成形を先に要求されず、その場で組み立てられるか |
| 型を変え、エラーを直し、変更を取り消す | 途中状態と元の入力を保持し、直し続けられるか |
| ネスト・配列・nullableを編集する | 深さや組み合わせによって操作規則が崩れないか |
| 対象やペインを切り替える | 選択、フォーカス、入力途中の状態を予測できるか |
| 大きな一覧やフォルダを扱う | 待ちや再描画で思考と操作を中断されないか |
| 保存し、成果物を生成する | 保存状態と成果物の正しさをそれぞれ理解できるか |

## 未決定のもの

実装言語、UI framework、内部の層構造、永続化形式、build / publishの具体的な契約は未選択。YAML / Git / MasterMemoryを含む既存技術の採否も、新しい要求と利用目的に照らして判断する。技術の再利用に先立って、GUIの作業と状態遷移を定義する。

CLIの開発とCLIへの互換性は、現在選択されている製品範囲に含まれない。将来CLIが必要になった場合は、その時点の目的から範囲と共有部分を判断する。

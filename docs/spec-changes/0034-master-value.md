# マスター値 — 単独の値の定義と利用

Status: Proposed

## 目的と根拠

プロジェクトで一つだけ決める値を、固定IDのレコードを作ったり検索したりせずに編集し、C#や通常のマスターデータテーブルから利用できるようにする。たとえば、編成人数の共通上限を一か所で変更し、個別の上限を指定したクエストだけはその値を維持できる。

ユーザーの要望は、一つの定義を論理的な1レコードとして扱い、キー・型・値を持つ項目を縦に並べること。通常テーブルのセルからの参照、キーの数値・文字列を選べる方向にも賛同があった。複数定義とファイル分割は検討事項として挙がった。以下の初版の範囲、採番、改名、Buildの扱いは設計提案である。

## UIでの呼び方

ユーザーの意向に合わせ、作成メニューには「新しいマスター値」、編集画面の種別には「マスター値」と表示する。項目の操作は「項目を追加」、列見出しは「キー」「プロパティ名」「型」「値」とする。本文中の `MasterValue` は英語の仮称とする。

## 定義と編集

プロジェクトに複数の定義を作れる。Explorerから定義名とキー方式（数値または文字列）を指定して作成し、空の項目一覧から編集を始める。定義を開くと各項目を次の向きで表示する。

| キー | プロパティ名 | 型 | 値 |
| --- | --- | --- | --- |
| 1001 | MaxPartySize | int | 4 |
| 1002 | AllowRetreat | bool | true |

- キー方式は定義単位。数値方式は非負の32ビット符号付き整数を扱い、追加時は未使用の番号を提案し、手入力もできる。文字列方式は空でない文字列を大文字小文字も含めて識別し、`"001"` は保存・再読込後も同じ文字列になる。項目またはその定義への参照がある間は方式を固定し、既存キーの暗黙変換を防ぐ。
- キーとC#プロパティ名はそれぞれ定義内で一意とする。定義名はプロジェクト内で参照先を一意に特定でき、生成するC#の名前とも衝突しないこと。文字列キーが有効なC#プロパティ名なら新規入力時の初期候補に使い、その後は個別に編集できる。C#に使えないキーでも、有効なプロパティ名を付ければ利用できる。
- 項目の追加・削除・並べ替えを行える。型と値の編集には通常のフィールドと同じ入力を使い、Enum、Flags、Value Object、Custom、配列、nullable、通常テーブルのレコードを選ぶ既存の参照設定も扱う。型の変更時は元の値を保持して不一致を示す。並べ替えてもキー、参照先、シリアライズ上のフィールド番号は安定する。
- 初版は `sources/` 内の1定義を1 YAMLファイルに保存する。キー、プロパティ名、型、値と項目順を往復でき、ファイルを移動しても論理的な参照先は同じ。分割する拡張では項目が自然な分割単位となるが、分割ファイルの作成・統合は初版の対象外とする。

## テーブルからの参照と変更時の挙動

通常テーブルの各データセルで直接値を入力するか、MasterValueの項目を選ぶ。候補は列と同じ型の項目に絞り、nullable、配列要素型、ユーザー定義型の違いも区別する。列全体を同じ入力方式に切り替える必要はない。初版の選択単位はセル全体とし、配列要素やCustomの子だけを個別に参照する編集、およびMasterValueから別のMasterValueを参照する連鎖は対象外とする。

参照セルは定義名・項目キーと現在値を確認でき、候補をキーとプロパティ名で検索できる。編集元には定義名と型を保ったキーの組を明示的な参照として保存し、同じ綴りの直接値とも区別する。参照を外して直接値にする際は現在の解決値を引き継ぐ。参照切れでも直接値の入力または別項目の選択で修正できる。

プロパティ名だけの変更は利用側のC#名に反映する。エディタで定義名やキーを変更した場合、一意に特定できる既存参照も同じUndo操作で更新する。削除・型変更・外部編集などで解決できなくなった参照は編集元に残し、参照元セルに対象と理由を示す。重複時は任意の候補を選ばない。意味エラーも途中保存でき、複数ファイルに波及した編集には既存の現在ファイル保存・全保存・外部変更検出の規則を適用する。

## Buildと利用側の契約

すべてのプロファイルに各定義の単一インスタンスを含める。利用側は、たとえば `db.BattleSettings.MaxPartySize` の形で固定IDや件数確認なしに型付きの値を取得できる。初版ではプロファイル別の値の上書きは扱わない。

Buildは選択対象の通常レコード内のMasterValue参照を実値へ解決し、直接入力した場合と同じC#フィールド型で出力する。解決値にも既存の主キー・一意性・レコード参照・プロファイル検証を適用する。定義側の参照項目がプロファイルで除外されたレコードを指す場合も診断する。値だけの変更は生成C#の公開形を維持する。生成バイナリを再読込できて初めてBuild成功とし、古い成果物のPublish防止も既存規則に従う。

DesktopとBrowserで同じ編集元を開き、編集・保存・再読込できる。CLIのinspectで定義とキー方式・項目を確認でき、validateとBuildはDesktopと同じ参照を解決する。既存の型やテーブルの改名でMasterValue側の型・レコード参照にも更新が必要な場合は既存の横断改名の対象に含める。専用CLI編集コマンドの設計は別途扱う。MasterValueを使わない既存プロジェクトには移行作業を求めない。関連仕様は [Desktop](../specs/desktop.md)、[Browser](../specs/browser.md)、[CLI](../specs/cli.md)。

## 受け入れ例

1. 数値方式のBattleSettingsと文字列方式のShopSettingsを作る。数値の自動採番と手入力、文字列キー `"001"` と独立したプロパティ名、同じキーを別定義で使えることを保存・再読込後に確認する。同一定義内の重複と無効なC#名は該当項目から修正できる。
2. クエストAの上限をBattleSettingsの1001への参照、Bを直接値3にする。1001の値を4から6へ変更し、再BuildしてC#から定義の値、A、Bの順に6、6、3を読み出す。プロファイルでAを除外しても定義の値は6で取得できる。
3. 1001のプロパティ名変更、並べ替え、ファイル移動を行い、Aの参照を維持する。次にキーを変更して参照の追従とUndo / Redoを確認する。全保存し、もう一方の編集環境で開き直して同じ結果を得る。
4. 1001の削除または型の不一致でAに理由が表示される。途中保存・再読込後も参照元を識別でき、対象を含むBuildは失敗する。参照先を戻すかセルを直接値に直すと再Buildできる。

## 承認範囲

今回の対象は仕様提案。英語の正式名と、将来の分割ファイル編集は初版の振る舞いを決める前提にしない。実装のObjectiveを選択した段階で、初版の範囲と既存仕様への影響を別passでレビューし、承認を判断する。

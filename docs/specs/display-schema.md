## 定義と編集

- スキーマと同じディレクトリの任意の付随ファイル（例 `items.yaml.view`）のルートに省略可能な配列 `functionColumns` と `formatRules` を置く。各要素は `name`（表示名）と `script`（同期JavaScript関数の本体を表す文字列）を持つ。配列順は表示順・ルール適用順を表す。通常列の `fields`、MessagePack key、PK / SK、参照、型定義は今までどおり実データを表す。
- 表定義のGUIで種別が分かり、両配列の追加・名称変更・複数行コードの編集・並べ替え・削除ができる。確定済みの各操作をSessionで取り消し・やり直しできる。未確定のコード入力は適用・取消の結果を明示し、別の項目に誤適用しない。JavaScriptの引数と戻り値が分かる編集支援を置く。
- 名前は同種の項目を特定できるようにし、通常列と関数列が同名の場合も診断する。不正な要素、空の名前、未完成のコードを保存・再読込できる。GUIで安全に編集できないshapeでは付随ファイルの位置と修正方法を示す。読み込んだ未知キーや不正値を暗黙に初期化しない。
- 定義を使っていないプロジェクトの読込・通常編集で付随ファイルを作らない。本文は標準YAMLを使い、旧版・CLIのYAML source探索から独立する。表示定義だけのSaveはスキーマYAMLを再シリアライズしない。スキーマの現在file保存・破棄・GUI上での移動と削除は付随ファイルを同じ単位で扱い、外部競合・失敗を同じ保存transactionで検査する。対応しない孤立ファイルを上書き・削除しない。定義の変更はGUI上で対象スキーマの表示設定をdirtyにし、保存と競合検査には既存の流れを使う。recordsの作成・複製、通常列のメニュー、キー・参照の候補、Build / C# / MasterMemoryは実フィールドを使う。CLI・Buildは付随ファイルを入力に含めない。CLIや外部ツールでschemaのpathを動かす場合は付随ファイルも同じpath規則で移す。列名を参照する任意のプログラムを自動書換えしない。
- 表示定義の問題は表示機能の診断とする。実データが有効なら表示コードの構文・評価失敗に左右されずBuildできる。

## 受入

1. 表示だけを編集・保存した場合は既存スキーマ・全dataファイルのbytesが一致する。定義のない既存スキーマで通常列を変更し再保存しても表示キーを作らない。分割dataファイルの実レコードと64bit整数も維持する。
2. GUIで関数列と二つのルールを作り、コードを編集して順序を入れ替え、Undo / Redo、保存・再読込して名前・順序・コードを照合する。操作中の取消や文書切替で別定義に入力が移らない。
3. 未完成・不正shape・未知キーのある定義を含むプロジェクトで他の編集と保存ができる。TS / Rust CLI・Buildの代表作業で表示コードや計算値が通常列・生成物に入らず、構造化編集後にも定義が残る。
